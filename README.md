# Конструктор опросов

REST-сервис для создания опросов и сбора ответов (упрощённый аналог Google Forms).
Автор создаёт опрос с вопросами и вариантами ответа и публикует его. Пользователи
проходят опрос и отправляют ответы. После этого автор закрывает опрос и смотрит итоги.

Учебный проект по дисциплине РБПО, вариант 19.

**Стек:** Java 25, Spring Boot 4.1, Spring Data JPA (Hibernate), PostgreSQL, Maven.

---

## Предметная модель

| Сущность | Таблица | Описание |
|---|---|---|
| Пользователь | `app.users` | пользователь системы: автор опросов или респондент |
| Опрос | `app.surveys` | название, автор, сроки проведения, статус |
| Вопрос | `app.survey_questions` | текст, признак обязательности, принадлежит опросу |
| Вариант ответа | `app.question_options` | допустимые варианты ответа на вопрос (с сохранением порядка) |
| Участие | `app.survey_participations` | прохождение опроса конкретным пользователем |
| Ответ | `app.survey_answers` | выбранный вариант на вопрос в рамках участия |

### Связи

```
users 1──* surveys              (автор опроса)
users 1──* survey_participations (респондент)
surveys 1──* survey_questions 1──* question_options
surveys 1──* survey_participations 1──* survey_answers
survey_questions 1──* survey_answers
```

### Жизненный цикл

```
Опрос:    DRAFT ──publish──► ACTIVE ──close──► CLOSED
Участие:  IN_PROGRESS ──submit──► SUBMITTED
          IN_PROGRESS ──(отказ респондента или закрытие опроса)──► ABANDONED
```

### Ограничения целостности (на уровне БД)

| Ограничение | Правило предметной области |
|---|---|
| `NOT NULL` + `CHECK (btrim(...) <> '')` | у пользователя, опроса, вопроса и варианта не может быть пустого имени или текста |
| `UNIQUE (email)` | один email принадлежит одному пользователю |
| `CHECK (status IN (...))` | статусы только из допустимого набора |
| `surveys_dates_order` | опрос не может закончиться раньше, чем начался |
| `question_options_unique_value` | варианты ответа внутри вопроса не повторяются |
| `participations_one_per_user` | пользователь проходит опрос один раз |
| `participations_submitted_at` | время отправки есть тогда и только тогда, когда участие отправлено |
| `answers_one_per_question` | в рамках участия на вопрос дан один ответ |
| `FOREIGN KEY ... ON DELETE CASCADE` | удаление объекта удаляет зависимые данные, и «висячих» ссылок не остаётся |

Правило «вопрос ответа принадлежит тому же опросу, что и участие» проверяется в сервисном слое.

## Бизнес-операции

| # | Операция | Запрос | Что делает | Когда отклоняется (409 Conflict) |
|---|---|---|---|---|
| 1 | Публикация опроса | `POST /api/surveys/{id}/publish` | DRAFT → ACTIVE; если дата начала не задана, ставит текущее время | опрос не в статусе DRAFT; в опросе нет вопросов; дата окончания уже прошла |
| 2 | Закрытие опроса | `POST /api/surveys/{id}/close` | ACTIVE → CLOSED; все незавершённые участия переводятся в ABANDONED; возвращает число брошенных участий | опрос не в статусе ACTIVE |
| 3 | Отправка участия | `POST /api/survey-participations/{id}/submit` | IN_PROGRESS → SUBMITTED; время отправки ставит сервер | участие уже отправлено или брошено; опрос не активен; срок опроса истёк; не отвечены обязательные вопросы (в ответе приходит их список) |
| 4 | Копирование опроса | `POST /api/surveys/{id}/copy` с телом `{"authorId": N}` | создаёт новый черновик «Копия: …» с копиями всех вопросов и вариантов для указанного автора | — (404, если опрос или автор не найден) |
| 5 | Итоги опроса | `GET /api/surveys/{id}/results` | число отправленных участий и количество выборов каждого варианта по каждому вопросу (учитываются только отправленные участия) | опрос в статусе DRAFT |

### Связанные правила

- Новый опрос всегда создаётся как DRAFT. Статус опроса меняется **только** операциями `publish` и `close`. Попытка изменить его через PATCH отклоняется (400).
- Вопросы можно создавать, изменять и удалять только в черновике. Чтобы изменить уже опубликованный опрос, его копируют (операция 4).
- Участвовать можно только в активном опросе и только в пределах его сроков.
- Отвечать и менять ответы можно только пока участие в статусе IN_PROGRESS. Значение ответа должно быть одним из вариантов вопроса.
- Участие отправляется только через `submit`. Через PATCH респондент может лишь отказаться от прохождения (`ABANDONED`).

### Корректность и целостность

- каждая операция выполняется в одной транзакции (`@Transactional`): она либо применяется целиком, либо откатывается;
- перед изменением проверяется текущее состояние связанных объектов;
- ограничения БД служат последним рубежом защиты (нарушение возвращается как 409);
- закрытие опроса и отправка участия блокируют строку опроса (`SELECT ... FOR UPDATE`), поэтому одновременные закрытие и отправка не могут привести к несогласованному состоянию.

## REST API (CRUD)

Для каждой сущности доступны операции:

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/{resources}` | 200, массив |
| `GET` | `/api/{resources}/{id}` | 200 / 404 |
| `POST` | `/api/{resources}` | 201, созданный объект с `id` |
| `PATCH` | `/api/{resources}/{id}` | 200, обновлённый объект (меняются только переданные поля) |
| `DELETE` | `/api/{resources}/{id}` | 204 |

`{resources}`: `users`, `surveys`, `survey-questions`, `survey-participations`, `survey-answers`.

**Коды ошибок:** `400` — некорректные входные данные, `404` — объект не найден,
`409` — операция недопустима в текущем состоянии или нарушает ограничение БД.
Тело ошибки: `{"error": "описание"}`. Тексты ошибок SQL клиенту не передаются.

## Безопасность доступа к БД

- приложение подключается к БД пользователем `survey_service`, которому разрешены только `SELECT, INSERT, UPDATE, DELETE` в схеме `app`. Создавать, изменять и удалять таблицы он не может;
- структурой БД владеет отдельный пользователь `survey_owner`;
- логин и пароль БД не хранятся в репозитории, а передаются через переменные окружения `DB_USER` и `DB_PASSWORD`;
- все запросы к БД параметризованы (Spring Data JPA / JPQL с параметрами), строки SQL из пользовательского ввода не склеиваются.

## Запуск

### 1. Подготовка PostgreSQL (один раз, от имени суперпользователя `postgres`)

```sql
CREATE ROLE survey_owner   LOGIN PASSWORD '<пароль владельца>';
CREATE ROLE survey_service LOGIN PASSWORD '<пароль сервиса>';
```
```sql
CREATE DATABASE surveys OWNER survey_owner;
```
Подключившись к базе `surveys`:
```sql
REVOKE ALL ON DATABASE surveys FROM PUBLIC;
GRANT CONNECT ON DATABASE surveys TO survey_owner, survey_service;
CREATE SCHEMA app AUTHORIZATION survey_owner;
GRANT USAGE ON SCHEMA app TO survey_service;
ALTER DEFAULT PRIVILEGES FOR ROLE survey_owner IN SCHEMA app
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO survey_service;
ALTER DEFAULT PRIVILEGES FOR ROLE survey_owner IN SCHEMA app
    GRANT USAGE, SELECT ON SEQUENCES TO survey_service;
```

### 2. Таблицы и тестовые данные

В базе `surveys` выполнить по порядку:
1. `db/schema.sql` — таблицы, ограничения, права;
2. `db/data.sql` — тестовые данные.

Повторный запуск этих двух скриптов сбрасывает БД в исходное состояние.

**Тестовые данные:** пользователи Иван (1), Мария (2), Олег (3); активный опрос
«Качество столовой» (1) с двумя вопросами, по которому Мария уже отправила ответы, а Олег
ответил не на все вопросы; черновик «Учебные курсы» (2) с вопросом; пустой черновик (3).

### 3. Запуск приложения

Задать переменные окружения и запустить:
```
DB_USER=survey_service
DB_PASSWORD=<пароль сервиса>
```
```
./mvnw spring-boot:run
```
Приложение доступно на `http://localhost:8080`.

## Коллекция запросов

`postman/surveys.postman_collection.json` — импортировать в Postman (Import → файл).

- **«1. CRUD по всем сущностям»** — создаёт свои данные, проверяет все CRUD-операции и
  ошибки валидации, затем удаляет созданное;
- **«2. Бизнес-сценарий»** — сценарий на тестовых данных: от исходного состояния через все
  пять бизнес-операций, включая отказы в недопустимых состояниях.

Каждый запрос проверяет ожидаемый HTTP-код (вкладка Tests), поэтому всю коллекцию можно
прогнать через Collection Runner. Перед повторным прогоном бизнес-сценария нужно сбросить БД
(шаг 2 запуска).
